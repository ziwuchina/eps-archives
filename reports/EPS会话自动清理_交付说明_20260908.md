# EPS COM 会话自动清理 · 交付说明（2026-09-08）

## 背景问题
EPS 作为 out-of-proc COM 服务器，每次 `CreateObject` 都会拉起独立 Eps.exe 实例，
客户端断开后**不会自动释放**。实测曾堆积 6 个实例，其中 1 个（PID 19872）死循环
100% 占满 CPU（属性导出超时残留），其余为历次会话残留。

## 交付物
1. `wrapper/eps_com_runner.py` — 通用运行器（所有后续 EPS COM 脚本统一使用）：
   - `run_vbs`：cscript 执行 + 弹窗自动关闭（SendMessageW BM_CLICK 0x00F5）
   - `snapshot_eps`：枚举 Eps.exe（PowerShell + FILETIME 启动时间作稳定指纹）
   - `run_and_clean`：快照 → 执行 → 清理本次新增实例（一键）
   - `cleanup_eps`：按"快照前集合 + 启动时间阈值"识别本次会话新增实例，
     只杀新增、**不动用户环境原有实例**（13008/19604 等）；失败自动延迟重试
     （EPS 断开 COM 客户端后需短暂释放，重试解决 Access denied 时序问题）
2. `wrapper/eps_parcel_batch_fast.py` — 已集成 runner（删除本地窗口处理死代码，
   改用 `er.run_and_clean`），业务结果不变（单会话 22.7s、12/12 坐标匹配）

## 实测验证（真实执行）
| 场景 | 新增实例 | 清理结果 | 会话后进程集 |
|---|---|---|---|
| 只读会话 ×1 | 1512 | 已杀 ✓ | = 运行前 |
| 只读会话 ×2 | 17824 | 已杀 ✓ | = 运行前 |
| 完整主流程（绘制12+验证+回读） | 23504 | 首杀 Access denied → 重试后已杀 ✓ | = 运行前 |

最终系统状态：仅剩用户环境原有 13008 / 19604（0 CPU、0 内存）+ 4380 空壳
（0 资源、Access denied 杀不掉、无害），**无任何本次工作残留进程**。
